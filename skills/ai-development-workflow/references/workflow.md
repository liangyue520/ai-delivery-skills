> 本文件遵守 [delivery-first](../../delivery-first/SKILL.md)，对所有项目生效。在用户授权和宿主规则允许时，主聊天可按需组织代理和委派相关聊天；主聊天统一收口，协作不扩大当前任务或恢复旧审批流程。

# 分阶段执行规范

## 目录
1. 接手与现状确认
2. 需求、数据与状态
3. 模块设计与拆分
4. 最小业务闭环
5. 功能迭代
6. 集成验收
7. 部署与交接
8. 复盘与维护
9. 通用运行控制

各阶段由主聊天按当前任务选用并统一负责，不要求顺序执行全部阶段。可按实际需要委派开发、分析或验证代理及相关Work，不按阶段机械另建角色或聊天；主聊天承担集成、必要验证和查漏，用户只决定必要业务事项。

## 1. 接手与现状确认

**进入：**项目对象和本轮目标可识别。

1. 阅读项目有效说明；核对源码、需求、数据库说明、样例及部署资料。
2. 确认当前版本、已有修改、启动入口和服务依赖。
3. 在允许的环境走一条与任务相关的代表性流程；无法运行时明确静态核对的限制。
4. 区分已有页面、已接接口、实际可用能力及历史声明。
5. 记录缺失条件、影响、本轮范围和后续入口。

**输出：**当前事实、入口、缺口、任务边界。

**完成：**知道当前能做什么、本轮改什么、什么条件会阻断。

**返回：**对象或目标不清，回到任务确认。不要把接手变成无边界全仓调查。

## 2. 需求、数据与状态

**进入：**目标和需求来源明确。

1. 写清用户、场景、操作、输入、输出与规则。
2. 明确对象身份、关系、来源、修改者及消费者。
3. 定义校验、审核、生效、退回、撤回和历史保留等相关状态。
4. 明确正式写入入口，以及失败、重复请求和部分成功如何处理。
5. 对照有效资料核对现有行为，开发前确定验收方法。
6. 列出待决策项、影响及确认人；推进不受影响的部分。

**输出：**足以实施的主流程、相关数据规则和关键待决策项；矩阵仅在确有需要时使用，不强制另建文档。

**完成：**关键规则足以支持设计；未决事项有边界及处理安排。

**返回：**目标冲突回任务确认，业务含义交业务确认人。

例：上传新资料B后，正式值仍为A；审核通过后才变为B。按实际业务确认该规则，不能从旧案例直接推定。

## 3. 模块设计与拆分

**进入：**关键规则、数据责任和预期结果明确。

1. 已有原型直接作为界面规格，优先复用布局、导航、字段和交互；检查现有组件、接口、数据结构及脚本能否复用，不为流程重做已确定的设计。
2. 明确页面入口、操作顺序、接口约定、数据责任、异常反馈。
3. 按影响核对旧数据、旧接口、配置兼容及必要恢复措施。
4. 需要分阶段时，每阶段形成可操作和验证的完整流程。独立任务可委派，说明输入输出、修改范围和真实依赖；同一文件或公共接口的耦合修改集中或串行处理，不建立下游准入和审批体系。
5. 明确验收方法、交付物、时间要求和停止条件。

**输出：**适度的实现方案与简短任务说明。

**完成：**可以直接实施，预期行为和验证方法清楚。

**返回：**方案依赖未定规则，回需求梳理。小修改可在任务记录中完成设计，不另写长文。

## 4. 最小业务闭环

**进入：**代表性流程、样例和预期结果明确。

1. 准备少量可预测结果的样例，标明测试数据。
2. 打通输入、处理、存储、展示或导出。
3. 核对同一对象的身份、数量和状态在各环节一致。
4. 验证决定正确性的关键分支，记录实际结果和缺口。

**输出：**可运行基础版本和业务链证据。

**完成：**从输入可追踪到最终结果，数据和状态符合预期。

**返回：**实现问题回实施；规则不成立回设计或业务确认。

例：样例导入→批次→校验→通过或退回→正式数据→查询核对。不要求其他项目照搬该业务。

## 5. 功能迭代

**进入：**相关设计和依赖清楚；复杂新链路需要时先完成最小闭环。

1. 按简短任务说明实施，保护已有和无关修改。
2. 完成一项执行相应验证，更新实际状态。
3. 新问题先分类，再决定是否纳入本轮。
4. 若发现影响实质扩大，说明原因和选择，按现有授权推进必要部分。
5. 提交结果、证据、未测项、遗留问题及下一步。

**输出：**模块交付、验证记录、问题清单。

**完成：**约定能力已接入实际入口，可以操作并完成相关验证，无未处理的阻断项。

**返回：**规则或方案改变回对应阶段；不顺带扩展无关能力。

## 6. 集成验收

**进入：**版本、依赖、环境、样例和验收标准一致。

1. 按用户顺序验证完整流程，核对跨模块身份、数量、状态和统计口径。
2. 根据影响验证异常、权限、兼容及约定性能。
3. 区分真实、测试和演示数据；不为了展示效果修改正式事实。
4. 记录通过、失败、未验证及对应证据。
5. 修复后复测受影响范围；通过后不无依据重复扩大检查。

**输出：**验收结果、遗留问题和交付判断。

**完成：**满足约定标准；限制、未完成和未测项清楚。

**返回：**主聊天组织修复失败环节并核实必要回归，关键业务口径冲突再询问用户。验证任务发现缺陷不自动授权修改。

验证强度：文案检查对应显示；逻辑覆盖主输入和关键分支；结构或写入变化核对兼容、旧数据和恢复；部署核对目标环境；AI效果使用固定样例及人工判断。性能要求使用约定指标，不能只写“不卡”。

AI应用按需核对：服务端凭据管理、输入输出校验、依据不足处理、超时重试和降级、重复业务写入、模型/提示词/知识版本、固定样例、业务正确性、人工复核及延迟费用要求。知识入库不等于训练模型，评分提高不等于业务效果提高。

## 7. 部署与交接

**进入：**交付版本、目标环境和相关操作授权明确。

1. 核对版本、依赖、路径、配置、网络和必要外部服务。
2. 按变更影响准备备份、恢复或回退办法，不擅自清理现有数据。
3. 使用实际交付入口部署，按变更影响验证启动、状态和必要的停止/重启；不无差别重启未受影响服务。
4. 在目标环境验证代表性业务；按要求验证离线或受限网络环境。
5. 交付日志入口、常见故障定位、恢复方式和已知限制。
6. 接收方能按说明完成必要操作；无法现场验证时明确未验证边界。

**输出：**交付包、维护说明、部署验证、版本及已知问题。

**完成：**可追溯、可运行、可检查、可恢复，达到约定交付标准。

**返回：**主聊天组织定位环境或功能问题。没有模型时至少能通过本地入口、配置、日志和复现资料开展维护。

## 8. 复盘与维护

**进入：**结果、遗留问题和实际记录可获得。

1. 对比预计和实际耗时，区分交互、执行、等待和必要核对。
2. 记录返工、依赖等待、无效尝试及原因。
3. 提炼可复用步骤、样例和脚本，区分通用经验与受限项目资料。
4. 为遗留项指定责任与下一步，不把未完成工作藏入归档。
5. 一次经验先作为案例；经复用验证后更新模板或技能。

**输出：**台账、改进项、案例或技能更新。

**完成：**结果和遗留项已说明，经验有适用边界。复盘仅在用户要求或实际复用需要时进行，不作为交付前置条件。

需要维护技能时，只保留有助于复用和判断的版本、变更原因、适用边界与实际验证，不新增能力盘点和例行维护报表。工具或规则变化、重复失败或输出无法使用时再按具体问题调整。

## 9. 通用运行控制

### 权限

阅读聚焦任务；修改保护原有工作；依赖调整确认必要性与兼容影响；数据库操作确认环境、保留与恢复；验证识别真实写入、外部调用和费用；发布、删除、对外发送核对相应授权。已有授权不重复确认，新增影响不隐瞒。

### 状态与问题

待开始→执行中→待验证→已完成。阻塞需写明依赖与恢复条件；暂停依据用户或优先级安排；取消说明目标已撤销。不能以“代码写完”认定验收通过。

问题分为阻断、非阻断、待决策、范围外。说明影响及责任，避免所有问题都阻断，也避免绕过影响正确性的关键问题。

### 异常恢复

保留状态→收集证据→判断影响→恢复/换方法/求助→验证→更新记录。页面无数据可沿业务应有数据、源数据、筛选身份、接口、页面逐层定位，按证据调整顺序。

必需输入缺失、无新证据、环境无法验证、影响越界或可能损坏数据时，停止相关依赖动作，保留交接和恢复条件。继续可独立推进的工作。不要机械凑重试次数或依据模型输出长度判断假死。

### 时间成本与结束

按复杂度明确优先级、时间要求、调查范围、验收和升级条件。需要时记录费用、调用、等待和复核。偏离预期时根据原因调整，不套用统一缓冲比例。达到验收条件且无阻断项后停止，新增优化另列任务。
