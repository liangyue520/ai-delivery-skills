# 主聊天统筹的开发与任务拆解

## 接手与范围

先核对用户最新目标、已有授权、相关源码/运行入口、现有修改、未解决问题和可复用成果。历史路径、报告和旧Prompt只作线索；不无边界全仓调查，不重建已有可靠设计。

已有原型直接作为界面规格，复用导航、布局、字段和交互。只将影响当前结果的具体业务冲突交用户判断，不要求设计、架构、数据、业务等角色分别审批。

## 实施顺序

1. 明确本轮用户能完成的操作和预期结果，识别必要的数据及规则。
2. 优先复用组件、服务、数据库和运行能力，只补确实缺少的接口、校验或数据关系。
3. 主聊天直接完成耦合修改；独立任务可委派代理或相关Work实施。统一接线和集成，先贯通正式入口到结果的完整流程。
4. 需要部署才能验证时，按当前授权更新必要服务并确认实际运行来源。
5. 主聊天组织受影响的业务检查，核实执行者的证据；失败时自行或委派修复并回归，通过后如实交付并停止。

按真实依赖安排先后，按需使用 [协作规范](agent-orchestration.md)。委派明确修改和验证范围，共享文件或公共接口集中或串行处理；保护既有修改，避免文件、服务和数据并发冲突。无需固定代理批次、领域负责人、文件准入或通用审批链。

## 简短任务说明

通常只需：目标、相关入口、范围、必要步骤、验收方法。可直接写在现有记录或对话中，不强制另建任务卡、任务树、看板、契约版本表或角色交接文件。

复杂任务按可用业务流程拆分阶段，明确真实依赖及未完成项；不以“先交页面/后接数据”为由长期推迟核心功能，也不把最小闭环解释成缩减用户完整需求。

## 变更与恢复

新问题先判断是否阻断本轮目标。必要修复在已有授权内继续；无关优化列为后续，不扩展当前任务。用户改变范围时更新当前说明，不要求分发、已读和接收回执。

修改前按影响准备必要备份或回退办法，不强制冻结版本、复制候选目录或比对哈希。部署和迁移见 [deployment-recovery.md](deployment-recovery.md)，业务数据检查见 [runtime-contracts.md](runtime-contracts.md)。

实际发生换人、换机或用户要求移交时，说明当前入口、修改、本次验证、未测项和下一步；日常委派只传递必要执行信息和结果，不制造多层交接。
